Deploying Telmoni in high-security production environments requires hardening database access, establishing automated audit partition rotations, configuring TLS reverse proxies, and transitioning authentication from quickstart passwords to enterprise Single Sign-On (OIDC).

## Identity & Authentication: Production OIDC Hardening

When first launching Telmoni, you can bootstrap an initial owner account using `ADMIN_EMAIL` and `ADMIN_PASSWORD`. However, **local username and password authentication is designed only for quickstarts, local testing, and evaluation**.

In a production deployment, **we strongly recommend connecting an enterprise OpenID Connect (OIDC) identity provider** (such as Okta, Keycloak, Microsoft Entra ID, Authentik, or Google Workspace) and disabling local password forms entirely.

### Why use OIDC in production?

1. **Centralized Lifecycle & Access Control**: When an employee leaves your organization or changes roles, deprovisioning their access in your IdP immediately blocks their Telmoni session.
2. **Enforce Enterprise MFA**: All multi-factor authentication (FIDO2 WebAuthn, hardware security keys, TOTP) is enforced upstream at your identity provider.
3. **Eliminate Password Attacks**: Removing local password forms eliminates credential stuffing, password spraying, and brute-force vectors against your console.

### Step-by-step transition to OIDC

<Steps>

1. **Configure your OpenID Connect Provider**

   Register Telmoni in your Identity Provider (IdP) with the following parameters:
   - **Allowed Redirect URI**: `https://telmoni.example.com/auth/callback`
   - **Scopes**: `openid`, `email`, `profile`

2. **Add OIDC variables to your environment**

   Configure the provider details in your `.env` or Kubernetes secret:

   ```sh
   # Identity Provider Discovery URL (must serve /.well-known/openid-configuration)
   OIDC_ISSUER=https://idp.example.com/realms/production
   OIDC_CLIENT_ID=telmoni-client-id
   OIDC_CLIENT_SECRET=telmoni-client-secret
   OIDC_REDIRECT_URI=https://telmoni.example.com/auth/callback
   OIDC_NAME="Corporate SSO"

   # Restrict self-registration
   OIDC_ALLOW_SIGN_UP=false
   ALLOW_SIGN_UP=false
   ```

3. **Verify OIDC sign-in**

   Restart the server and log in using the newly available **"Continue with Corporate SSO"** button. Confirm that your user identity logs in and gains administrative access.

4. **Disable the local password form**

   Once OIDC login is verified, remove `ADMIN_EMAIL` and `ADMIN_PASSWORD` from your environment and set:

   ```sh
   DISABLE_LOGIN_FORM=true
   ```

   > [!IMPORTANT]
   > The Telmoni server performs sanity checks at boot:
   > - If `DISABLE_LOGIN_FORM=true` is set without a configured `OIDC_ISSUER`, the server halts immediately because nobody could sign in.
   > - If `ADMIN_EMAIL` is set alongside `DISABLE_LOGIN_FORM=true`, the server halts because a password account could never log in. Remove `ADMIN_EMAIL` before enabling `DISABLE_LOGIN_FORM`.

</Steps>

## Database role hardening

Telmoni enforces strict least-privilege principles at the database layer. In a production cluster, the application modules should never connect as a PostgreSQL superuser. 

### Role separation

The database tier is split into four distinct roles:

```text
┌─────────────────┬────────────────────────────────────────────────────────┐
│ Role            │ Granted Capabilities                                   │
├─────────────────┼────────────────────────────────────────────────────────┤
│ migrator        │ Owns all tables, schemas, and views. Runs DDL.         │
│ auth            │ CRUD on accounts, orgs, projects, and RBAC tables.     │
│ notifications   │ CRUD on delivery queues, feeds, and connector records. │
│ agent           │ Read/write on document chunks and vector embeddings.   │
└─────────────────┴────────────────────────────────────────────────────────┘
```

### Applying role hardening

To apply the production hardening policies, run the superuser setup script provided in the repository:

<Steps>

1. **Create the login roles**

   Connect as a superuser to the database Telmoni will use, and create the service roles and the `vector` extension. The hardening script looks for these exact role names and stops if one is missing. The extension belongs to one database, not the cluster, so it must be created in Telmoni's own: the agent's tables need it, only a superuser can create it, and the migration stops without it or on a version before 0.8:

   ```sql
   CREATE ROLE migrator WITH LOGIN PASSWORD 'migrator_secure_password';
   CREATE ROLE auth WITH LOGIN PASSWORD 'auth_secure_password';
   CREATE ROLE notifications WITH LOGIN PASSWORD 'notifications_secure_password';
   CREATE ROLE agent WITH LOGIN PASSWORD 'agent_secure_password';
   CREATE EXTENSION IF NOT EXISTS vector;
   ```

2. **Execute hardening script**

   Apply `crates/migrator/sql/role_hardening.sql`:

   ```bash
   psql "$SUPERUSER_DATABASE_URL" -v ON_ERROR_STOP=1 -f crates/migrator/sql/role_hardening.sql
   ```

   This script:
   - Strips `SUPERUSER`, `CREATEROLE`, and `CREATEDB` from all service roles.
   - Enforces `NOBYPASSRLS` across `auth`, `notifications`, and `agent` so that application pools cannot bypass PostgreSQL Row-Level Security policies.
   - Locks down default permissions in the `public` schema.

3. **Run migrations and apply object grants**

   Execute the migrator as the `migrator` user:

   ```bash
   MIGRATOR_DATABASE_URL="postgres://migrator:migrator_secure_password@postgres:5432/telmoni" \
     telmoni migrate
   ```

   The migrator automatically executes `object_grants.sql`, granting only the specific `SELECT`, `INSERT`, `UPDATE`, and `DELETE` privileges each service module needs to operate.

</Steps>

## Audit log partition rotation

Telmoni's audit log uses range-partitioned tables partitioned monthly by timestamp (`created_at`). To maintain query performance and ensure partitions exist ahead of time, run the rotation command:

```bash
telmoni rotate
```

### Rotation behavior

- **Forward Runway**: `telmoni rotate` creates the current calendar month and the next three months of partitions ahead of time (`{table}_YYYY_MM`). It never drops audit partitions (`drop_enabled: false` in `crates/shared/src/db/retention.rs`).
- **Idempotency**: Safe to run continuously; if partitions exist, no changes are made.

### Scheduling via cron or systemd timer

Run the rotation job once per week (or once per day):

```bash
# /etc/cron.d/telmoni-rotate
0 3 * * 0 root docker compose -f /opt/telmoni/deploy/compose/docker-compose.yml run --rm migrate rotate
```

## Operator CLI sweeps & disaster recovery

The `telmoni` binary includes administrative commands for cluster operators.

### Background maintenance sweeps

While `telmoni serve` runs scheduled background sweeps in its main loop, you can trigger individual maintenance jobs on demand:

```bash
# Execute soft-deletion cleanup saga (permanently purges organizations past 14-day grace)
telmoni sweep deletion

# Verify cryptographic hash chain across the audit ledger
telmoni sweep audit-verify

# Delete revoked API keys, stale invitations, revoked sessions and spent sign-in grants
telmoni sweep retention

# Re-embed every agent passage that a previous EMBEDDINGS_MODEL embedded
telmoni sweep agent-reindex
```

### Emergency organization management

If an organization needs to be terminated or recovered manually by a platform administrator:

```bash
# Immediately suspend an organization and enter the 14-day soft-deletion window
telmoni terminate org_019a0b8c3f2e7d41

# Restore a suspended organization within the 14-day grace period
telmoni restore org_019a0b8c3f2e7d41
```

## Reverse proxy configuration

In production, place Telmoni behind a reverse proxy that terminates TLS and forwards to the web console on port `3000`. Every request from outside enters there, the `/v1` API's included: the server on port `8082` answers only callers carrying the service secret. Never expose either port directly to the public internet.

**What the console expects of the proxy.** The console's rate limiter takes each caller's address from `X-Forwarded-For`: the second address from the end when the header holds two or more, the only address when it holds one, and `X-Real-IP` when it is absent. The proxy in front of the console must therefore overwrite `X-Forwarded-For` with the address it saw the client at, as both configurations below do, rather than append to what the client sent: behind a single appending proxy, a client that sends its own `X-Forwarded-For` chooses the address it is metered as. (The second-from-the-end rule exists for a load balancer that appends the client's address and then its own, as Google's does.)

The console's live updates (server-sent events) and the agent's streamed answers are marked `X-Accel-Buffering: no`, so Nginx passes them through unbuffered. The console uses no WebSockets.

<Tabs>
  <TabItem label="Caddy (Recommended)">
    Caddy automatically provisions and renews Let's Encrypt / ZeroSSL certificates:

    ```nginx
    # /etc/caddy/Caddyfile
    telmoni.example.com {
        encode zstd gzip

        # Next.js Web Console
        reverse_proxy localhost:3000 {
            header_up Host {host}
            header_up X-Real-IP {remote_host}
            header_up X-Forwarded-For {remote_host}
            header_up X-Forwarded-Proto {scheme}
        }
    }
    ```
  </TabItem>
  <TabItem label="Nginx">
    Nginx with TLS, forwarding to the console. `X-Forwarded-For` is set to `$remote_addr`, the address Nginx saw the client at, never to `$proxy_add_x_forwarded_for`, which would append it to whatever the client sent:

    ```nginx
    # /etc/nginx/sites-available/telmoni.conf
    server {
        listen 80;
        server_name telmoni.example.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl http2;
        server_name telmoni.example.com;

        ssl_certificate /etc/letsencrypt/live/telmoni.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/telmoni.example.com/privkey.pem;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers HIGH:!aNULL:!MD5;

        client_max_body_size 25M;

        location / {
            proxy_pass http://127.0.0.1:3000;
            proxy_http_version 1.1;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $remote_addr;
            proxy_set_header X-Forwarded-Proto $scheme;

            # Timeouts for the event streams
            proxy_read_timeout 86400s;
            proxy_send_timeout 86400s;
        }
    }
    ```

    If Nginx itself sits behind another proxy or load balancer, `$remote_addr` is that hop's address and every client shares one rate-limit bucket; use Nginx's `real_ip` module (`set_real_ip_from`, `real_ip_header`) so that `$remote_addr` is the client's address again.
  </TabItem>
</Tabs>

## Backups & disaster recovery

### PostgreSQL backups

Telmoni stores all persistent state in PostgreSQL. Create periodic physical or logical backups using `pg_dump`:

```bash
# Logical database dump
pg_dump -U telmoni -d telmoni -Fc -f "/backups/telmoni_$(date +%Y%m%d_%H%M%S).dump"
```

To restore from a backup file:

```bash
pg_restore -U telmoni -d telmoni --clean --if-exists "/backups/telmoni_backup.dump"
```

> [!IMPORTANT]
> If your deployment uses `CONNECTOR_KEK` for encrypting connector tokens at rest, always safeguard and backup your encryption key alongside your database dumps. Restoring database rows without the matching key will make connector credentials permanently unreadable.
